### 进程、线程、协程的区别，python里为啥多线程处理cpu密集型任务效果不好，如果都是IO密集型，python里异步和多线程用哪个


+ 进程：资源分配
+ 线程：调度
+ 协程：底层是单线程

---

全局解释器锁，同意时刻只有一个<font style="background-color:#FBDE28;">线程</font>在CPU上执行Python字节码

处理CPU密集型任务时，多线程会频繁进程GIL锁， 导致大量时间浪费在线程上下文切换与锁的争夺上，性能往往比单线程还要差。  

> <font style="background-color:#FBDE28;">Python 处理 CPU 密集型任务应使用 </font>**<font style="background-color:#FBDE28;">多进程</font>**<font style="background-color:#FBDE28;">。每个进程有独立的 Python 解释器和 GIL 锁，可以真正做到多核并行  </font>
>

---

优先选择异步（`asyncio`）的场景

+ **超高并发：** 需要同时处理成千上万个连接（如高并发 Web 服务、大型网络爬虫）。
+ **资源敏感：** 协程开销极低（单个协程仅占几 KB 内存，而一个线程通常需要几 MB），支持轻松创建数十万个协程。

优先选择多线程的场景

+ **依赖阻塞式第三方库：** 如果项目中大量使用了不支持异步的阻塞库（如传统 `requests`, `pymysql`），改为 `asyncio` 需要重构底层代码；而多线程可以直接包装现有的同步阻塞代码**并行执行**。

> `asyncio` 的核心是“主动让出（yield）控制权”。但像 `requests` 这种库，其代码逻辑里压根没有写 `await` 或任何配合事件循环的调度代码，只要调了它，整个 Python 线程就会被迫卡死等待。 
>
> 
>
>  为什么多线程能“解除”这种阻塞？   
>
>  操作系统将这个线程挂起，并将 CPU 资源切给线程池里的**其他线程**。  
>

内层的 `wrapper` 函数可以访问外层 `retry` 传入的 `max_times` 和中层 `decorator` 传入的 `func`

```python
@retry(max_times=3, delay=1.0)
def unstable_api():
    ...
等价于在后台自动执行了下面这行代码：
unstable_api = retry(max_times=3, delay=1.0)(unstable_api)  
```
