## 第一章：底层通信与核心组件模型

### 1.1 五者架构全景图

- **生产者** publish 绑定 exchange 设置 routing_key（routing_key 在 exchange 中用于绑定队列 = 路由规则 key 给哪一个队列）
- **交换机** topic
- `queue_bind(exchange=, queue=, routing_key=)`
- **队列**
- 交换机（1/N）———绑定———队列（1/N）
- **消费者** `consume(queue=, on_message_callback=callback_func, auto_ack=)` + `.start_comsuming()`
- **回调函数**：生产者生产消息时带 reply_to、correlation_id，生产者侧会建立一个回调队列然后监听，reply_to 就是回调队列的名字。消费者 reply 的时候 routing_key=reply_to 同时带上 correlation_id 用于生产者校验

> 生产者—交给（不需要关心队列了）—交换机—绑定—队列—监听—消费者

### 1.2 通道（Channel）的核心哲学与线程安全

#### 为什么需要 Channel（多路复用 Multiplexing）？

- **TCP 开销高昂**：TCP 三次握手/四次挥手及心跳维护极大消耗系统资源。
- **多路复用设计**：全局维护少量 TCP **Connection**，每个线程/协程单独开辟逻辑独立的 **Channel** 串行收发指令，大幅降低内核 Socket 开销。

#### ⚠️ 严禁跨线程共享 Channel 的底层原理

官方协议强制要求：**一个 Channel 只能由一个线程持有，严禁跨线程共享！**

#### Q：Thread A 试图写一个 basic.publish 的消息头帧；同一瞬间，Thread B 试图写另一个 basic.ack 的确认帧；两个线程的数据包会在底层 TCP Buffer 中交织混杂，导致发送给 RabbitMQ 的 AMQP 帧序列损坏（Frame Corruption）。不是会有序列号吗？

TCP 报文头部的 Sequence Number（序列号），作用是**保证网络数据包在到达对端后，能按照发送顺序重新组装成连续的字节流**。

但是，TCP **完全不知道也不关心**你的应用程序发的是什么数据！在 TCP 眼里，你传给它的全部都是无差别的 `010101` 字节。

**假设没有锁保护，多线程向同一个 Socket 写入时会发生什么？**

在操作系统层面，多个线程共享一个 Socket，本质上是多个线程同时向同一个操作系统 Socket 发送缓冲区（Send Buffer）写入字节：

假设 Thread A 准备发送一个 `basic.publish` 帧，共 10 个字节：`[A1, A2, A3, A4, A5, A6, A7, A8, A9, A10]`

同一瞬间，Thread B 准备发送一个 `basic.ack` 帧，共 5 个字节：`[B1, B2, B3, B4, B5]`

由于操作系统在多线程并发写入 Socket 时，并没有 AMQP 级别的原子锁保护，写入操作在字节层面发生了交替插队（Interleaving）：

最终写入 TCP 缓冲区的字节流变成了：`[A1, A2, A3, B1, B2, A4, A5, B3, B4, B5, A6, A7, A8, A9, A10]`

TCP 的处理结果：TCP 确实会为这串交错后的字节打包，附加上 TCP Sequence Number 发给 RabbitMQ 服务端。RabbitMQ 的 TCP 协议栈收到后，利用 TCP 序列号完美还原了这串字节：`A1 A2 A3 B1 B2 A4 A5 B3 B4 B5 A6 A7 A8 A9 A10`

2. **Delivery Tag 作用域冲突**：

- `Delivery Tag`（交付流水号）是单调递增整数，**作用域仅限当前 Channel**。
- 若 Thread B 执行 `basic_ack(delivery_tag=6, multiple=True)`，会直接在当前 Channel 上误 ACK 掉 Thread A 正在处理的 `Tag 5` 消息。

## 第二章：端到端高可靠与数据一致性

### 2.1 消费端幂等性（Idempotency）设计

当消费者崩溃、网络闪断或未及时 ACK 时，RabbitMQ 会自动将未确认消息重新入队，消息的 `redelivered` 标志会被设置为 `true`。为防止重复消费引发业务异常（如重复扣费、重复调用 API），必须在消费端做幂等处理。

#### 生产级 3 大幂等方案

1. **全局 Message ID + Redis 去重表（推荐）**：
   - 生产者注入全局唯一 `message_id`。
   - 消费者利用 Redis `SET key value NX EX seconds` 抢占原子锁，抢占失败直接 ACK 丢弃重复消息。
2. **数据库唯一索引（Unique Key Constraint）**：
   - 将业务流水号/任务 ID 设为数据库主键。重复插入触发 `DuplicateKeyException` 时，捕获异常并手动 ACK 丢弃。
3. **状态机控制（Status Machine）**：
   - 只有当当前业务状态为 `INIT` 时才允许执行更新，若已为 `SUCCESS` 则直接跳过。

### 2.2 生产端可靠性：事务机制 vs 发布者确认（Publisher Confirms）

为了确保消息成功到达 Broker，AMQP 提供了两种方案：

```text
 ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
 │                                   生产端可靠性选择                                          │
 ├─────────────────────────┬───────────────────────────────────────────────────────────────────┤
 │ 机制                    │ 特点与性能                                                        │
 ├─────────────────────────┼───────────────────────────────────────────────────────────────────┤
 │ 事务机制 (tx_select)     │ 同步阻塞，每发一条需死等存盘，吞吐量骤降 250 倍，生产环境已废弃！  │
 │ 发布者确认 (Confirm)    │ 异步非阻塞，通过 channel.confirm_select() 开启，性能高，生产首选。  │
 └─────────────────────────┴───────────────────────────────────────────────────────────────────┘
```

#### “生产端 ACK”与“消费端 ACK”对比

| 维度 | 发布者确认 (Publisher Confirm ACK) | 消费者确认 (Consumer ACK) |
| --- | --- | --- |
| **发送方** | **RabbitMQ Broker** | **消费者 (Consumer / Worker)** |
| **接收方** | **生产者 (Producer)** | **RabbitMQ Broker** |
| **作用** | 保证消息成功入队/存盘，不丢失 | 保证消息被成功业务处理，未处理完可重试 |

## 第三章：性能、背压与海量积压控制

### 3.1 消费端背压机制与 Prefetch Count（QoS）

#### 自动确认（Auto-ACK）的致命隐患

开启 `auto_ack=True` 时，MQ 会瞬间将上万条消息推入客户端内存 Buffer。对于 Agent 推理（如耗时 10 秒/条）等重型任务，会导致客户端**内存暴冲（OOM）**，触发操作系统 **Swapping**，进而卡死进程。

#### 手动确认 + `basic.qos(prefetch_count=N)`

`prefetch_count=N` 告知 MQ：“**若本地有 N 条未确认消息，停止推送新消息！**”

#### Prefetch Count 选型指南

- **长耗时/重型任务（如 Agent 推理、视频转码）**：**必须设置 `prefetch_count = 1`**。确保“按需分配、公平分发（Fair Dispatch）”，防止任务在某节点堆积发呆。
- **轻量高吞吐任务（如日志处理）**：**推荐设置 `prefetch_count = 10 ~ 100`**。抵消网络往返延时（RTT）开销。

### 3.2 深度剖析：传统队列 vs 流（Stream）海量积压处理

> 队列（Queue）是“用完即销毁”的传统消息通道（基于 FIFO 破坏性读取）；而流（Stream）是“可重复消费”的现代追加日志存储（Append-Only Log，类似 Apache Kafka）。

| 对比维度 | 传统队列（Classic / Quorum Queue） | 流（Stream） |
| --- | --- | --- |
| **底层数据结构** | **破坏性 FIFO 队列**（Destructive Read） | **只追加日志**（Append-Only Log） |
| **消息消费后的去向** | 消费者发送 `ACK` 后，消息立刻被**物理删除** | 消息**永久保留**（除非达到设定的磁盘容量或 TTLRetention 限制） |
| **消费模型** | **推模型（Push-based）**为主：MQ 主动推给 Worker | **拉模型 / 游标偏移量（Offset-based）**：消费者按 Offset 自由读取 |
| **多消费者模式** | **竞争消费（Competing Consumers）**：多 Worker 瓜分同一条队列里的消息，用于平摊负载。 | **独立重放（Fan-out / Replay）**：多消费者各自维护自己的 Offset，独立完整读取一份完整的数据。 |
| **并发与保序** | 多消费者并发处理时**无法保序**（需退化为单活消费者 SAC） | 支持**流过滤（Stream Filtering）**，实现多消费者并发处理不同子集的同时**局部严格保序**。 |
| **内存与磁盘占用** | 理想情况下队列长度接近 0，内存/磁盘占用极小 | 长期保存历史数据，依赖高性能磁盘（NVMe/SSD），占用更多磁盘空间。 |

#### 1. 什么时候选【队列（Queue）】？

- **核心业务任务调度**：如 Agent 任务分发、订单处理、邮件发送。
- **要求“恰好处理一次/不能重复处理”**：任务被某个 Worker 拿到处理完后，必须立刻从队列里消失，防止其他 Worker 重复消费。
- **需要死信队列（DLX）、延迟重试等复杂 AMQP 路由特性**。

#### 2. 什么时候选【流（Stream）】？

- **海量数据吞吐（百万级 TPS）**：需要极高写入性能（Stream 性能远超普通 Queue）。
- **需要“消息重放（Message Replay）”**：例如系统崩溃后，新上线的 Worker 需要**从昨天中午 12 点的偏移量开始重新读取数据**修复数据库。
- **广播 / 多订阅模式（One-to-Many）**：同一个事件（如“用户注册成功”），需要同时给营销服务、风控服务、日志服务各自完整推一份，且互不干扰。
- **大模型 Agent 的上下文/历史对话日志存储**：需要按时间顺序追加，并能按 Offset 随时回溯历史调用的场景。

#### Q：当希望将同一条消息发送给多个订阅者时，用户目前必须为每个消费者绑定一个专用队列。为什么不可以多个消费者绑定同一个队列吗？

> 如果让**多个消费者监听同一个队列，RabbitMQ 的默认行为是“竞争消费（Work Queue）”**——即一条消息只会被**其中一个**消费者抢到，而不是广播给所有人。

- **破坏性读取**：消息被消费者成功 `ACK` 确认后，就会立刻从队列中**物理擦除**。
- 如果有 100 个消费者监听同一个队列，当一条消息发出来时，RabbitMQ 必须在内存里记录：**消息 $M_1$ 是否被 Consumer 1 ~ 100 分别 ACK？**

### 4.2 仲裁队列（Quorum Queues）与死信队列（DLX）

> - **仲裁队列**解决的是 **“消息服务的高可用与强一致性（服务端怎么保证自己不丢消息/不宕机）”**；
> - **死信队列**解决的是 **“异常消息的处理与兜底机制（消费失败/异常的消息该去哪里）”**。

#### 一、 仲裁队列（Quorum Queues）—— 高可用强一致存储

##### 1. 核心原理：基于 Raft 共识算法

仲裁队列由 **1 个 Leader（主节点）** 和 **多个 Follower（副本节点）** 组成（通常建议 3 或 5 个节点的奇数集群）。

- **多数派写入确认（Majority Consensus）**：
  1. 生产者发送消息到 Leader 节点。
  2. Leader 将消息日志同步给各个 Follower 节点。
  3. 当**超过半数（N/2 + 1）** 节点（例如 3 节点中的 2 个，5 节点中的 3 个）成功将消息写入磁盘后，Leader 才会给生产者返回 `Publisher Confirm` ACK 确认。
- **故障自动转移（Leader Election）**：如果 Leader 节点挂掉，存活的 Followers 会在毫秒级内通过 Raft 算法选举出拥有最新日志的 Follower 提升为新 Leader，**保证已 ACK 的数据绝对不丢失**。

##### 2. 仲裁队列的关键特性

1. **强一致性与持久化**：强制消息落盘存储，数据安全性极高。
2. **非阻塞增量同步**：当宕机的节点重新上线时，仲裁队列**不需要阻塞全量同步**，而是只增量追赶缺失的 Raft 日志，不影响主流程的正常读写。
3. **防毒丸消息死循环（Delivery Limit）**：内置 `x-delivery-limit` 参数。如果某条消息因为报错不断重新入队（`requeue=True`），达到设定的重试次数上限（如 5 次）后，仲裁队列会自动将该消息丢弃或**自动发送到死信队列**。

#### 二、死信队列（Dead Letter Exchange / Queue, DLX/DLQ）—— 异常消息的“垃圾回收站”

**死信队列**并不是一种特殊的队列存储结构，而是一种**处理异常消息的架构设计模式**。当一条消息在普通队列中变成“死信（Dead Letter）”时，RabbitMQ 会自动将其转投到一个专门的死信交换机（DLX），进而路由到死信队列中暂存，等待人工干预或延时重试。

##### 1. 消息在什么情况下会变成“死信”？（3 大触发条件）

1. **消息被拒绝**：消费者调用 `basic.reject()` 或 `basic.nack()`，并且设置 **`requeue=False`**（告知 MQ “这条消息我处理不了，且不要把它重新放回原队列”）。
2. **消息超时过期（TTL Expired）**：消息在队列中达到了设定的生存时间（Time-To-Live），却一直没有被消费。
3. **队列达到最大容量（Max Length Exceeded）**：队列设置了最大消息条数或字节数限制，当新消息入队且队列已满时，队头的旧消息会被丢弃或送入死信队列。

##### 2. 死信队列的工作流程

```text
┌────────────┐   1. Publish    ┌──────────────┐   2. 消费失败 basic.nack(requeue=False)
│  生产者    │ ──────────────> │  主业务队列  │ ──────────────────────────┐
└────────────┘                 └──────────────┘                           │
                                      │                                   │ 触发死信机制
                                      │ 3. 变成死信                        │
                                      ▼                                   │
                               ┌──────────────┐                           │
                               │  死信交换机  │ <─────────────────────────┘
                               │    (DLX)     │
                               └──────┬───────┘
                                      │ 4. 路由
                                      ▼
                               ┌──────────────┐   5. 人工排查 / 离线分析 / 延迟重试
                               │  死信队列    │ <───────────────────────── [ 告警&监控 ]
                               │    (DLQ)     │
                               └──────────────┘
```

#### Q：如何设计一个 100% 不丢消息且不重复处理的系统？

- **生产端**：开启 **Publisher Confirm** 模式，未收到 ACK 则重试/落库。
- **Broker 端**：使用 **仲裁队列（Quorum Queue）** + 消息持久化（`durable: true`）。
- **消费端**：使用**手动 ACK** + 设置 `prefetch_count=1`，业务层结合 **Redis `SETNX` 全局 Message ID** 保证幂等性。
