## 为什么用？

- 节点宕机自动断点续传：从断点继续，不会从头开始（不会重复调用前 4 步已经成功的昂贵 API）
- 支持超长等待与人工干预（Human-in-the-Loop：挂起等待外部人工审批信号）
- 通过声明式配置 Activity 级别的指数退避、超时控制与熔断逻辑

## 是什么样的？

1. **Workflow（指挥官）**：负责业务逻辑的流转与状态编排。必须运行在确定性沙箱中，严禁直接发起任何 I/O、网络请求、获取当前时间或生成随机数。
2. **Activity（执行者）**：任何随机性 / 高 I/O 任务交给 Activity，Activity 完成后把确定结果传给 Workflow。Activity 实例在 Worker 中共享，代码必须设计为无状态（线程安全）与幂等（Idempotent）。
3. **Replay（重放）**：Temporal 服务端保存一份只增不减的 Event History。当 Worker 崩溃恢复或被唤醒时，会从头重新运行 Workflow 代码。遇到已经执行过的 Activity 时，直接从历史记录中读取返回值注入，从而复原到崩溃前的状态。
4. **三大消息机制**获得 Workflow 内存状态（Workflow ID: "agent-job-1001"）
   - Query = GET
   - Signals = POST
   - Updates = gRPC，修改状态并同步获取返回值
5. 一旦后续步骤失败且重试耗尽，可以通过 Python 的 `try...except` 捕获异常，并在 `except` 块里依次调用预先定义好的**补偿 Activity**，实现分布式事务的自动回滚（如撤销订单、扣减库存）。

## 场景处理

- 经过多次指数退避重试后仍然彻底失败 → 状态挂起 + 高警报推送 + 人工介入信号恢复
- 长流治理：清空当前工作流历史事件，继承最新状态，从而实现无限运行
- 子工作流：`主 Agent 流程` → `子工具链 Workflow`
- 拦截器：统一分布式链路追踪、Token 消费量自动统计、全局超时控制、动态权限校验
- 异步活动
- **持久化计时器**：在 Workflow 中写 `await workflow.sleep(days=30)`，Temporal 会在数据库中注册一个 Timer 事件并挂起该工作流。休眠期间占用 0 CPU 和 0 内存，即使服务器中途重启，计时器精度依然精准无误。
- **调度**：Temporal Schedules 提供了原生的分布式 Cron 调度能力，具备重试、冲突检测、补偿漏跑任务（Backfill）等完备特性。

## Agent 架构与 Temporal 映射关系

```text
 ┌─────────────────────────────────────────────────────────┐
 │               AI Agent 系统 (业务层)                    │
 │                                                         │
 │  [ LLM 大脑 ] <──> [ Context/Memory ] <──> [ Tools 手脚 ] │
 └────────────────────────────▲────────────────────────────┘
                              │ 运行在...
 ┌────────────────────────────▼────────────────────────────┐
 │               Temporal 引擎 (底层基础设施)               │
 │                                                         │
 │  • Workflow ──> 驱动 ReAct 循环，维护 Agent 内存状态       │
 │  • Activity ──> 封装 API/工具调用，处理 429/重试/限流       │
 │  • Signal   ──> 接收人工干预、补充输入 (Human-in-the-Loop)│
 │  • Query    ──> 外部实时读取 Agent 当前思考步骤与状态     │
 └─────────────────────────────────────────────────────────┘
```
