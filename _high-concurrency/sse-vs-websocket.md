# LLM 打字机场景首选 SSE

LLM 生成场景的特点是“单向下行”（客户端发 1 次 Prompt，服务端连续推送数百/数千 Token）。在这个前提下：

SSE 优势

- 支持多路复用
- 网关吞吐量更高：纯 Socket 流式 Flush，开销极低（不用维护双向 Frame 解析与读写 Buffer）
- 断线自动重连：浏览器原生 `EventSource`（不用前端手动写心跳、重连与 Ack）
- 100% 标准 HTTP，穿透所有 7 层网关（需网关/负载均衡显式配置 Upgrade）

```text
┌──────────────────────────────────────────────────────────┐
│ 应用层 (Application Layer)  : SSE (text/event-stream)    │ ─── 规定数据格式: event/data/id\n\n
├──────────────────────────────────────────────────────────┤
│ 传输编码层 (Transfer Layer) : Chunked / HTTP/2 DATA Frame│ ─── 规定数据如何被切块传输
├──────────────────────────────────────────────────────────┤
│ 传输层 (Transport Layer)    : TCP / TLS                  │
└──────────────────────────────────────────────────────────┘
```

# 客户端与 LLM API 交互，是采用 TCP 还是 UDP？

大模型输出的是文本 Token（或者 JSON 数据包）。在文本传输中，**绝对不能出现“丢包”、“乱序”或“数据损坏”**。→ 可靠传输 = TCP

# TCP 是怎么保证可靠传输的？

**校验和、序列号与确认、重传机制、流量控制、拥塞控制、连接管理**。

---

## 1. 校验和（Checksum）：基础毁损检测

- **作用**：检测数据在传输过程中是否发生了位变异（损坏）。
- **机制**：发送方将 TCP 伪首部、TCP 首部和数据联合计算出一个 16 位的校验和放入报文头。接收方收到后重新计算，如果校验和不匹配，说明数据已损坏，**接收方会直接静默丢弃该报文块，不回传 ACK，等待发送方超时重传**。

---

## 2. 序列号与确认应答（Sequence & ACK）：去重与防乱序

- **序列号（Sequence Number, `seq`）**：TCP 是**按字节**编号的。发送方发出的每一个字节都有唯一的序号。
- *解决问题*：接收方依靠序号对乱序到达的报文进行**重新排序**，并**过滤掉重复接收**的报文。
- **确认应答（Acknowledgment, `ACK`）**：接收方收到数据后，回复一个 `ACK` 报文，告诉发送方 `ack = N`。
- *含义*：“我已经成功收到了编号 `N-1` 之前的全部数据，**请你下一次发送从第 `N` 个字节开始的数据**”。

---

## 3. 重传机制（Retransmission）：丢包补救

网络中发生丢包或 ACK 丢失时，TCP 会通过以下三种重传手段进行补救：

```text
【超时重传】   发送方发送数据 ──▶ 超时定时器到期仍未收到 ACK ──▶ 重传数据包
【快速重传】   接收方收到 seq 1,3,4,5 ──▶ 连续发送 3 次 ACK 2 ──▶ 发送方不等超时，立刻补发 seq 2
```

1. **超时重传（Timeout Retransmission / RTO）**：
   - 发送方发包时会启动一个动态计算的计时器（基于 RTT 往返时间）。如果在指定时间 RTO 内没收到 ACK，就认定丢包，**触发重传**。
2. **快速重传（Fast Retransmission）**：
   - 不依赖超时定时器。当接收方发现中间漏掉了一个包（例如收到了 `包1`、`包3`、`包4`，缺失 `包2`），就会连续触发 3 次相同的重复 ACK（`ACK 2`）。发送方收到**连续 3 个重复 ACK** 时，立即重传缺失的 `包2`。
3. **选择性确认（SACK / Selective ACK）**：
   - 在 TCP 选项中带上已收到的不连续数据块范围（如：`已收到 100~200 和 300~400`）。发送方能够精准得知哪些包丢了，只重传真正缺失的数据，避免盲目重传全部数据。

---

## 4. 流量控制（Flow Control）：保护接收方不被“撑爆”

- **痛点**：发送方发得太快，接收方的缓存区（Socket Receive Buffer）来不及处理，会导致溢出丢包。
- **解决方案：滑动窗口（Sliding Window）**
- 接收方在给发送方回复 `ACK` 时，会在报文头的 **`Window` 字段**填入自己当前**剩余的缓冲区大小（即通告窗口 `rwnd`）**。
- 发送方根据 `rwnd` 动态调整自己的发送窗口大小。如果 `rwnd = 0`，发送方会**停止发送数据**（进入窗口探测状态），直到接收方腾出空间。

---

## 5. 拥塞控制（Congestion Control）：保护整个网络不被“挤爆”

- **痛点**：如果整个网络路由器处于拥堵状态，盲目重传只会让网络雪上加霜。
- **解决方案**：拥塞窗口（`cwnd`）与四大算法
- 发送方维护一个根据网络状况动态变化的**拥塞窗口 `cwnd`**。发送方的实际发送能力上限为：`Min(rwnd, cwnd)`。

```text
 拥塞窗口 cwnd
       ▲
       │                                     /│ 发生拥塞 (丢包/超时)
       │                                    / │ ──▶ 降回到 1 或减半
       │                     /│/│/│        /  │
       │                   /  ││││       /   │
       │                 /    │ (拥塞避免)
       │      /───┐     /
       │     / (指数)  /
       │    /         /  (慢启动)
       └────┴─────────┴────────────────────────▶ 时间
```

1. **慢启动（Slow Start）**：连接刚建立时，`cwnd` 从 1 开始以**指数级**增长（1 $\rightarrow$ 2 $\rightarrow$ 4 $\rightarrow$ 8...），快速探测网络容量。
2. **拥塞避免（Congestion Avoidance）**：当 `cwnd` 达到慢启动门限（`ssthresh`）后，改为**线性增长**（每轮 RTT $+1$），平稳增加发送速率。
3. **快重传与快恢复（Fast Recovery）**：当发生快速重传（收到 3 个重复 ACK）时，判定网络只是轻微拥堵，不将 `cwnd` 直接降回 1，而是减半后再线性增长，快速恢复吞吐量。

---

## 6. 连接管理（Connection Management）：协同与状态确认

可靠传输的前提是建立和释放连接时，双方对于初始序号和状态达成一致：

- **三次握手（3-Way Handshake）**：
  - 同步双方的**初始序列号（ISN）**。
  - 协商最大的报文段大小（**MSS**）和窗口缩放因子。
  - 确认双向的发送与接收能力正常。
- **四次挥手（4-Way Handshake）**：
  - 确保双向的数据都已经完整传输完毕后再关闭连接。
  - 主动关闭方进入 `TIME_WAIT` 状态（保持 2MSL 时间），确保最后一个 ACK 能够送达对方，并消耗掉网络中残存的旧报文。

---

## 📝 总结表

| 维度 | 解决的核心问题 | 关键机制/概念 |
| --- | --- | --- |
| **毁损** | 字节传输错误 | 校验和 (Checksum) |
| **丢包/乱序** | 包丢失、颠倒、重复 | 序列号 (`seq`)、确认号 (`ACK`)、重传机制 (RTO/SACK) |
| **端侧溢出** | 接收方缓冲区不够用 | 滑动窗口、流量控制 (`rwnd`) |
| **网络瘫痪** | 中间路由器网路拥堵 | 拥塞窗口 (`cwnd`)、慢启动、拥塞避免算法 |
| **协同断链** | 状态不同步、遗留数据干扰 | 三次握手、四次挥手 (`TIME_WAIT`) |
