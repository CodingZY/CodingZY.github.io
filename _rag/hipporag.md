> 纯 Graph 有图无文，HippoRAG 让最后检索的是**段落 P**

## 为什么论文中没有与 GraphRAG 进行对比实现？

- **GraphRAG 的设计目标**：主要用于**全局 / 主题式查询微调与总结**，即回答类似“这份文档集的主要主题是什么？”等高层级总结问题。它在离线阶段通过 LLM 对图节点进行自底向上的分层聚类和社区总结。
- **HippoRAG 的设计目标**：侧重于**多跳精准事实检索**

## 计算实体节点之间的向量余弦相似度，若高于阈值，则建立同义词边，为什么不直接将同义词合并？那这样不是有很多种边：实体关系边、上下文边、同义词边，不是会显得很冗杂？？

> `Apple Inc.`（苹果公司）和 `Apple II`（苹果电脑产品），或者 `Obama` 和 `Michelle Obama`，它们的向量相似度可能高达 0.85+。如果直接硬合并（Hard Merge），一旦合错了，这两个节点的**局部关系网**就会直接**坍塌**在一起，导致**全局拓扑结构污染**。

从“关系数据库”或“传统知识图谱”的角度看，这些边确实显得杂乱；但如果从 PageRank 能量扩散通道的视角来看，边（Edges）本质上只是概率流动的管道，类型再多也不会造成算法灾难。HippoRAG 内部都会将它们归一化为矩阵中的权重 $W_{ij}$

**同义词合并和不合并怎么平衡？**

## 离线索引

LLM 对每个段落进行三元组抽取，建立实体关系边

embedding 计算 Node 的预先相似度，建立同义词边

矩阵映射：构建一个节点-段落出现矩阵 $P \in \mathbb{R}^{\vert{}N\vert{} \times \vert{}P\vert{}}$，记录各名词短语在原始段落中的出现频次

- $\vert{}N\vert{}$ 是整个知识图谱中**所有实体节点**的总数量。
- $\vert{}P\vert{}$ 是检索语料库中**所有段落**的总数量。
- **矩阵单元** $P_{i,j}$：代表第 i 个实体节点在第 j 个段落中出现的频次。

## 在线检索

1. Query 提取实体，embedding 将实体映射到图谱中，作为**种子节点**
2. 🌟**节点特异性**：$s_i = \vert{}P_i\vert{}^{-1}$（$P_i$ 为所有段落包含该节点的次数）
3. PageRank 流动图检索
4. 段落打分：获得更新后的节点概率分布 $\vec{n'}$ 后，计算 $\vec{p} = \vec{n'} P$

### 需要把图遍历一遍得到等数不是很耗时吗？

你直觉上觉得“遍历图很慢”，是因为将它想象成了深度优先搜索（DFS）或广度优先搜索（BFS）那种串行递归的过程。但 HippoRAG 的实现完全不同：

1. **代数化求解（矩阵迭代）**：PPR 算法在数学上是通过稀疏矩阵向量乘法（SpMV）实现的。在 GPU 上，这种乘法可以高度并行化，通常只需 10~20 次简单的矩阵迭代就能收敛。
2. **只在局部子图扩散**：阻尼因子设置为 0.5 时，概率衰减极快，概率只会从 Query 种子节点向外扩散 2~3 步（多跳范围），计算量被严格限制在极小的局部节点范围内。

> $\vec{n}^{(k+1)} = (1 - \alpha) \cdot M \cdot \vec{n}^{(k)} + \alpha \cdot \vec{v}$
>
> 代表在每一步扩散中，随机游走有 **50% 的概率**沿着图中的边（关系边、同义词边）继续向前扩散去探寻邻近节点；同时有 **50% 的概率**回初始的 Query 种子节点。

## HippoRAG2 和 HippoRAG 的区别？

| 维度 | HippoRAG (一代) | HippoRAG 2 (二代) |
| --- | --- | --- |
| 图谱结构 (KG Construct) | 仅短语节点 (Phrase Nodes)<br>图谱节点仅由提取的概念短语构成，造成信息压缩与上下文丢失。 | **引入文章节点 (Passage Nodes)** 作为“浓密编码”，通过包含关系边连接“稀疏编码”的短语节点，保留完整上下文。 |
| 查询匹配 / 链接方式 | 实体链接 | 采用**文本嵌入将整个 Query 直接匹配到图谱的三元组（Triples）**上，精准捕捉语义关联。 |
| 种子节点选择机制 | 仅根据提取的实体向量相似度直接确定 PPR 的初始种子节点。 | 采用“**Retrieval + LLM Triple Filtering**”两步法，在种子节点确定前由大模型过滤无关三元组。 |
| PPR 游走重置概率 | 仅赋予短语节点 | **短语节点 + 文章节点联合分配** |
| 综合任务表现 | **多跳 QA 表现优异，但在简单事实 QA（Factual QA）和长文本理解（Sense-making）上明显逊色于传统向量检索。** | 不仅在多跳联想检索上比最强向量模型（NV-Embed-v2）提升约 7%，且在简单事实与长文本理解任务上均全面超越传统 RAG。 |

## LightRAG、GraphRAG、HippoRAG 的关系和区别？

**擅长场景**

适合全书 / 全数据集级别的**宏观总结**（全局 Query，如“数据集的主题是什么？”）。

兼顾**局部细节抽取与全局综合理解**（全场景均衡）。

```text
[原始文本 Chunk] 
       │
       ▼ (LLM 提取 & Dedupe)
[知识图谱 (实体 Nodes + 关系 Edges)]
       │
       ├─────────────────────────────────┐
       ▼                                 ▼
[Low-Level Keys: 实体名]        [High-Level Keys: 抽象主题/关系关键词]
       │                                 │
       └────────────────┬────────────────┘
                        ▼
               [用户 Query 触发 LLM]
                        │
         ┌──────────────┴──────────────┐
         ▼                             ▼
  [抽取 Local Keywords]      [抽取 Global Keywords]
         │                             │
         └──────────────┬──────────────┘
                        ▼
               [向量数据库混合检索]
                        │
                        ▼
             [构建 Context 生成回答]
```

- **Low-level Keys**：直接将实体名称（Entity Name）作为 Key。其 Value 包含实体的类型、详细描述以及对应的原始文本 Chunk 切片
- **High-level Keys**：利用 LLM 从抽取出的关系及全局上下文中提取高阶抽象主题/关键词（Global Themes/Keywords）作为 Key。其 Value 包含对应的关系描述以及相连实体的全局主题。
- **实体去重与图融合（Deduplication）**：自动合并从不同切片中提取到的同名实体和关系，避免节点冗余，降低后续图检索计算量。
- 无需重新聚类或重新生成全局社区报告

擅长**多跳推理**，处理需要连接多个隐性关联信息的复杂问题。
